Solo developer workflow: 14 stages from idea to launch and operations

Updated 2026-11-14 · Section entries verified 2026-11-13, see each section page

A solo project passes through 14 stages from idea to launch and operations: idea validation, code hosting, models and APIs, databases, authentication, deploy and hosting, servers and VPS, domains, object storage, email, monitoring and analytics, peripheral capabilities, payments and monetization, and launch and operations. Each stage connects to its section page, or to a key-points card on this page where no section page exists.

Stages follow project order, not a one-time setup of everything: earlier stages get decided first, and later stages after the product shape is set. Free allowances, card requirements, and overage rules for each stage are on the corresponding section pages.

Launch checklist from zero

Work through the items in order, finishing each before moving on; note skipped items and complete them before launch.

Idea & development

  1. Write one sentence: whose problem, and what problem.
  2. Talk to a few potential users; ask about past behavior, not “would you use it”.
  3. Build a landing page or a waitlist; check whether anyone leaves contact details.
  4. Set the scope of the first usable version: one core feature.
  5. Put the code in a repository; decide the branching and deployment approach. See Code hosting.

Deploy & launch

  1. Pick a deployment route: a managed free tier, web hosting, or a VPS. See Deploy & hosting, Web hosting, Free VPS.
  2. Pick a database; confirm the idle-pause and overage rules. See Databases.
  3. Decide the auth approach: build it or use managed auth. See Authentication.
  4. Set up the domain, DNS, and SSL. See Domains & DNS.
  5. Store files and images in object storage, not in the code repository. See Object storage.

Operations essentials

  1. Set up registration verification and notification email. See Email.
  2. Monitoring and alerts: uptime alerts, error tracking, access analytics. See Monitoring & analytics.
  3. Arrange scheduled tasks and queues.

Monetization & growth

  1. Payment method: fees, tax handling, payout path. See Payments.
  2. Pre-launch checks: backups, billing alerts, status page.

Stack 1: Vercel + Supabase + R2

  • Vercel Hobby: 100 GB Fast Data Transfer, 1M CDN requests, 1M function invocations, 4 CPU hours; no top-up purchases once the limit is reached; personal or non-commercial use only.
  • Supabase: 500 MB database, 50,000 MAU, 5 GB egress, 1 GB file storage; free projects pause after 1 week inactive; max 2 active projects.
  • Cloudflare R2: 10 GB-month storage per month, 1M Class A operations, 10M Class B operations, free egress.
  • Optional additions: Resend (3,000 emails/month, 100/day), Clerk (50,000 MRUs per application).

Stack 2: Cloudflare full stack

  • Cloudflare Workers: 100,000 requests/day, 10 ms CPU per invocation; bundled free amounts include KV 100,000 reads/day, D1 5M row reads/day, Queues 10,000 ops/day.

  • Cloudflare R2: 10 GB-month storage per month, 1M Class A operations, 10M Class B operations, free egress.
  • Cloudflare Free plan: $0, including DNS, CDN, Universal SSL.

Method guides: key points

Three stages have no section page. The key points for each follow.

Stage 1 · Idea validation: key points

  • Validation means confirming, before writing code, that someone will spend time, money, or contact details on the idea.
  • Three low-cost methods: a landing page with a waitlist, manual concierge service, and interviews about past behavior.
  • Signals that count are concrete actions: leaving contact details, paying a deposit or prepaying, asking follow-up questions, already paying for an alternative.
  • Common mistakes: asking “would you use it”, building the full product before validating, treating likes as demand, asking only people nearby.
  • After validation: set the first version to one core feature solving the confirmed problem.

Stage 12 · Peripheral capabilities: key points

  • Peripheral capabilities are the supporting capabilities beyond the main feature: scheduled tasks, message queues, search, and caching.
  • Main-stack built-ins come first: capabilities built into the deploy platform, database, or monitoring service, before adding a separate service.
  • Scheduled tasks are fixed-time automated work: nightly cleanup, hourly data pulls, weekly summaries. Failures need alerts.
  • Queues run slow work in the background: sending email, generating images, processing uploads — users do not wait for the result.
  • Search and caching: small content volumes work with database fuzzy queries; caching needs an expiry time, or stale data keeps serving as new.

Stage 14 · Launch & operations: key points

  • Pre-launch checks: uptime alerts, error tracking, access analytics, and a status page.
  • Backups: keep backup files off the same machine as the database, and rehearse a restore — whether a backup restores is only known after a rehearsal.
  • Billing and usage: overage behavior differs by entry — service stops or charges start; usage alerts before the limit avoid sudden stops or surprise bills.
  • Domains, email, and certificates: verification and notification email set up with domain verification; renewal prices differ from first-year prices; free certificates have renewal rate limits.
  • After launch: a change log entry per release, a feedback channel, weekly monitoring review, regular billing review with unused services shut off. Acquisition channels where target users gather; privacy policy, user agreement, and filing requirements depend on the regions served — information only, not legal advice.
