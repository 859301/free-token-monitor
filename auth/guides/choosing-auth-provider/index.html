自己写要做的事

自己写登录注册，注册、登录、会话、密码重置、社交登录对接、组织管理这些环节都要自行实现，出了问题也自行处理。好处是没有厂商额度上限与超限规则；代价是实现与维护的工作量都在自己这边。

用认证服务要看的数字

免费用户量：Clerk 按 MRU 计（50,000 MRUs/应用），Auth0 按 MAU 计（至多 25,000 MAU），口径不同，数字不能直接比大小，见MRU 与 MAU 有什么不同。社交登录与企业连接：Clerk 至多 3 个社交登录，Auth0 1 个企业连接。组织：Clerk 100 MROs/应用，Auth0 5 个组织。绑卡：两家注册都不需要信用卡，Auth0 的自定义域名需绑卡验证。超限：Clerk 写明强制升级与 1 个月宽限期，Auth0 超限行为以官方页面为准，见认证额度超了怎么办。

已经用数据库的

已经用 Supabase 或 Firebase 做数据库的，附带认证额度随数据库免费档提供：Supabase Auth 50,000 MAU，Firebase Auth 50K MAU。完整规格见数据库板块的Supabase 详情页与Firebase 详情页。只需要认证、不需要数据库的，看独立认证服务的免费档。

决定步骤

  1. 确认用户量级与口径：看 MRU 还是 MAU，定义原文见口径指南。
  2. 确认社交登录数量：需要几个社交登录，或是否需要企业连接。
  3. 确认组织需求：需要多少组织，Clerk 按 MRO 计，Auth0 按组织个数计。
  4. 确认绑卡与自定义域名：注册绑卡要求与自定义域名绑卡验证分开看。
  5. 确认超限规则：超限后是强制升级、有宽限期，还是以官方页面为准。
